# CALIBRI v59 — RATE-FIRST ≤0.70 effective bpw + direct packed weight inference

**Experimental objective reprioritized by user.** Stop attempting to preserve all task accuracy and 20% warm speed in the FIRST stage. Instead **first produce a physically verified entire pretrained weight archive ≤0.70 bits/UNIQUE original parameter, with a model that performs end-to-end inference directly from resident compressed weights**. THEN improve quality and optimize speed in later independent stages. This is motivated by QMoE (Frantar & Alistarh, *Practical Sub-1-Bit Compression of Trillion-Parameter Models*, arXiv:2310.16795): a storage format **co-designed with custom compressed-execution kernels**, rather than the old CALIBRI v58 INT6 at rest + dense FP32 model on cold load. QMoE achieved ~0.8bpw on huge sparse SwitchTransformer MoE, which is NOT the same as demonstrating 0.7bpw on a dense instruction model. AQLM (Egiazarian et al., ICML 2024) and QuIP# (Tseng et al., ICML 2024) suggest vector/codebook structured representations for sub-4-bit dense models but provide NO claim of competent 0.7bpw model without expensive calibration.

## Frozen FIRST-stage CB59 representation — physical complete model, not a projection

Source is same pretrained `HuggingFaceTB/SmolLM2-135M-Instruct` original public BF16->FP32 CPU checkpoint, SHA `12fd25f77366fa6b3b4b768ec3050bf629380bac`, independently verified v58: **134,515,008 UNIQUE source parameters**, tied `lm_head.weight` and `model.embed_tokens.weight`; no double counting. No task/training/test text is used for compression in this rate-first stage.

Choose **K32V8** source-only vector codebook quantization:
- Partition every unique pretrained FP32 2D tensor row into consecutive **8-element vectors**. A tensor-local **32×8 FP16 centroid dictionary** is trained from a deterministic subsample of up to 4096 *source weights only*; 5 fixed Lloyd iterations. Uncalibrated source-only weights, no labels or validation/test texts.
- Choose the nearest centroid for every 8-value source-weight group after normalization by a per-row RMS scale; store one **5-bit integer centroid index per eight original FP32 weights**, i.e. **0.625 raw bits/weight** across 2D matrices. All codes packed densely LSB-first (8×5-bit codes per 5 bytes) into a REAL physical file.
- Each matrix stores exactly **32×8 FP16 centroid values = 512 bytes**, and **one FP16 row scale for every original matrix output row**. Original 1D norm/bias vectors stored losslessly in FP32. Full state names, shapes, source alias mapping, per-tensor segments included as explicit JSON manifest.
- Entire **CB59** physical archive is a byte-stream with version, metadata and payload lengths, CRC32 and SHA256. **ALL overhead**, tied metadata, codebook dictionaries, scales and actual full 1D weight bytes count toward **`floor(0.70×134,515,008/8)` actual byte hard cap**. There is NO sidecar hidden outside file to make rate appear smaller. No hypothetical zero-weight free lunch.
- Original source-weight relative RMSE per matrix and source-global root MSE are recorded. This codebook prototype **may destroy source language competence even though storage ≤0.70bpw**; do not label it a successful quality-preserving model unless measured.

## Direct compressed execution — source-specific C fused lookup-GEMV

**NO entire weight matrix is reconstructed during inference.** Kernel `direct_kernel_v59.c` does:
1. For each input 8-element group, precompute a tiny activation-dependent 32-centroid dot-product lookup table **LUT[g,code]** (size groups×32, not rows×groups×8).
2. For each compressed output row, read **5-bit codes directly from the resident physical packed checkpoint**; gather the corresponding LUT entry per group and sum, multiplying the FP16-on-disk row scale (decoded once as tiny metadata). This produces the output activation without any dense pretrained FP32 W or matmul.
3. For tied embedding and output head: embedding gathers and reconstructs only **requested token rows** (not entire vocabulary matrix), and the LM output head performs the same direct packed 5-bit LUT-GEMV over the shared compressed tensor handle.
4. Replace all pretrained Llama `nn.Linear` and `nn.Embedding` modules with these packed-only operators. Require zero surviving pretrained 2D dense parameters, shared handle identity for tied vocabulary matrices, and exact matching names/shapes. Native C library compiled by GCC in independent CI, exposed via Python ctypes. The initial C implementation prioritizes verifiable correct direct inference over optimal speed.
5. Test on a genuine freshly initialized architecture loaded *from_config* and a separate CB59 physical file; this separate process **must NOT load original trained weights or any source teacher tensors**. Verify a complete real input 8-token forward pass, finite full-vocabulary logits and an additional 1 autoregressive step with actual KV cache. Compare source-teacher logits from a DIFFERENT independent process (normalized output RMSE, KL divergence, exact next-token top1 match). If quality is disastrously degraded, report as such, DO NOT conceal.

## Frozen first-stage acceptance and limitations

**Rate-first target:** actual entire complete trained source physical checkpoint **≤0.70 effective bits per source UNIQUE trained parameter**, and live FULL pretrained architecture forward + KV continuation works directly with resident 5-bit codes and no dense pretrained 2D matrix reconstruction. Both must be confirmed on Ubuntu22/24 (PyTorch2.5.1 CPU, Transformers4.46.3, NumPy1.26.4, pinned source SHA, OpenBLAS 1 thread and Torch 2 threads). Third independent checker validates real physical byte sizes, SHA, model geometry, source hashes, C direct operation with no teacher process and all finite actual logits.

**Quality phase intentionally deferred but not omitted from evidence:** also record actual source-weight RMSE, original→packed normalized logit RMSE, next-token KL divergence, top-1 agreement, and real paired CPU timings. None is allowed to be silently omitted. Under **no circumstances** interpret source-model finiteness as preservation of semantic correctness, user-task ability, or nonfatal quantization errors. If quality is terrible, rate-format + native operator is an **infrastructure experiment only**, and subsequent accuracy recovery must be a separate goal. Real speed can be slower than original BLAS; user explicitly reprioritized compression first.

**No claims** that QMoE itself works on this dense 135M model at 0.7bpw, no fake sub-bit gain from non-unique tied matrices, no claim to reach QMoE GPU kernel performance or to have passed the previous user's ≤20% speed target (temporarily deferred at user's direction). ## Initial v59 CI finding and determinism correction (audit note)

Initial two-host experiment run **41506607704** confirmed actual full source **11,229,303 physical bytes = 0.6678394 bpw**, complete end-to-end packed native CPU forward/KV on both hosts, zero dense pretrained 2D hot weights, **but crosshost CB59 SHA hashes differed**. The first learned FP16 centroid assignments used CPU floating-point BLAS nearest-neighbour scoring; slightly different CPU rounding produced different bitstreams, so third strict checker correctly FAILED. Also first-run quality on one frozen prompt is visibly poor: pretrained-vs-packed output **KL ~10.28 nats**, normalized logits RMSE **~0.576**, next-token prediction changed; direct CPU speed ratio ~1.5–2.94x original for 8-token prefill+one decode. These numbers establish that <=0.7bpw was a functioning *storage/direct-compute prototype*, NOT a quality-preserving solution; no production readiness claim.

For cross-CPU stability, changed **only SOURCE-ONLY codebook assignment arithmetic** before the next CI: each normalized pretrained source 8D group and centroid is snapped to FP16 (already the source storage format) and then to a deterministic 1/128 integer grid, and each nearest-centroid selection uses exact int32 dot / int64 squared-distance, with FP16-rounded centroid Lloyd updates. The modified quantizer is a new codec subversion within v59 (quality metrics must be freshly measured); **not** optimized using task labels or hidden QA data. The actual validation prompt was already observed in first run, so it should be treated as a development smoke diagnostic and NOT an untouched blinded semantic quality benchmark. Third checker still requires byte-for-byte identical CB59 on independent CPUs. The original threshold <=0.70bpw and native execution requirements are unchanged.
